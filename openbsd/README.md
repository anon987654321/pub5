# OpenBSD

Phase 2 of the pub5 migration. This tree is not a production deployment
target yet. The production host remains on pub4 until the database and upload
restore, rehearsal, application parity and rollback gates pass.

## Configuration ownership

- \`registry/apps.yml\` owns deployed app names and ports.
- \`registry/openbsd.yml\` owns relayd, PF and rc.d serving policy.
- \`registry/schemas/openbsd.yml\` and \`registry/schemas/apps.yml\` validate
  those inputs through \`Core::Registry\`.
- \`proven/\` contains approved pub4 configuration fixtures, kept unchanged.
- \`etc/relayd.conf\`, \`etc/pf.conf\` and \`etc/rc.d/*\` are generated mirrors.
  Other files still present under \`etc/\`, \`usr/\` and \`var/\` are legacy
  source material and are not generated by the Phase 2 renderer.

## Local check and generation

\`bin/openbsd check\` compares registry output against both the proven fixtures
and generated mirrors. It also checks app ports, registered Host matches and
rc.d code skeletons.

\`ruby openbsd/bin/render_configs.rb --write\` writes only the generated
relayd, PF and rc.d files through the core capability manifest and atomic
writer. It never changes \`proven/\`, runs a service manager, opens SSH or
deploys.

## Not yet migrated

The legacy deploy, installer, broker, DNS and recovery scripts remain
unqualified for pub5. Do not run \`redeploy\`, \`vps-deploy\`, \`OPERATOR.sh\`
or the old vm23 runbook as a pub5 deployment procedure. The next Phase 2
work is the single Mac-built artifact/deploy tool, followed by a separate-VM
rehearsal. \`registry/hosts.yml\` records deployment and restore evidence as
BLOCKED / NOT_RUN.

\`RUNBOOK.md\` remains a historical pub4 operational record until its commands
and paths are deliberately ported and proven for pub5.
